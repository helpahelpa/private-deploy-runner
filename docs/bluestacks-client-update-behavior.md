# Main BlueStacks: pipeline publication versus installed client updates

## Answer

**Running the reviewed pipeline with client changes publishes tested client artifacts; it does not itself install another Android client or silently replace Main's installed APK.** Existing-client incremental updates and user-confirmed APK upgrades are separate mechanisms. Two historical Main icons can instead reflect the **different package identities** `com.fl.mhsy.qihoo` (retired Opening) and `com.fl.mhsy.privateworld` (current Main), not two copies created by successive privateworld pipeline builds.

Sources below are repository-relative: **runner** = `/home/user0/mhsy/mhsy-deploy-runner`; **game** = `/home/user0/mhsy/mhsy-offline-revival`. This is a source-only review, not confirmation of live runtime state.

## Four distinct operations

1. **Build and publish artifacts.** Broker runs `build_client.py`, verifies client receipts/assets/APK, merges generated assets, and copies the signed APK into release `assets/client.apk` only when `publish_apk` is true (default true). See runner `scripts/broker.py:364-368,385-416`. The documented public path is `/client.apk` (runner `README.md:388-395`). The optional registry callback invokes only the fixed `sync_registry.py` command (runner `scripts/broker.py:504-509`). That script copies the release APK to configured filesystem `distribution_apk`, preserves installed `apk_sha256` and per-install routing, updates world/ingress pins, and explicitly records `automatic_installation: False` (runner `scripts/sync_registry.py:26-43,62-63`). **Updating a distribution file is not updating an emulator's installed app.**

2. **Incremental game/content updates (no Android package installation).** Builder outputs a new incremental pack, update configuration and server list; the incremental asset counter is independent of the Android package version (runner `docs/client-build.md:11-21`). Game packager writes `Android_90/UpdateRoot/IncrementPack/<version>/...` and `update_config.json`'s `server_versions.Android_90` (game `launch-build/prepare_multiplayer_client.py:363-373`). The game update server advertises the channel's version/IncrementPack URL and serves those files (game `server/update_server.py:97-106,126-157`). This is the existing game's asset-update path, **not a second installed client and not replacement of Java/C# APK payloads**. Actual uptake depends on the running client's update flow, configured endpoints and connectivity; publication alone does not prove it has downloaded the release.

3. **APK upgrade through startup UI.** Current startup reads `assets_origin`, fetches update metadata, and offers an upgrade only if the advertised Android version code exceeds the installed one (game `launch-build/multiplayer-client/StartupActivity.java:92-108`; endpoint implementation: `UpdateHttp.java:31,44`). Download/install and defer/continue are explicit buttons; installation uses Android's `ACTION_INSTALL_PACKAGE` and user confirmation, with install-source permission handling when applicable (`StartupActivity.java:53-71`). Policy pins `com.fl.mhsy.privateworld`, signer, and `/client.apk` (`ApkUpdate.java:11,33-41`); archive validation requires the installed/downloaded package identity to match, the signer to match, and a newer version (`UpdateInstaller.java:28-33`). Thus this is an **in-place same-package upgrade**, not a package migration or duplicate-install mechanism. Native APK inputs are fingerprinted separately; unchanged inputs reuse the exact signed APK/version, while a cache miss reserves a new Android version (runner `scripts/build_client.py:208-222,444-459,495-497`; `docs/client-build.md:13,19`). A new asset release does not necessarily produce an APK upgrade offer.

4. **Explicit operator installation through Main launcher.** `launch-main-world.ps1` requires package `com.fl.mhsy.privateworld`, instance `Rvc64`, serial `emulator-5554`, and ADB port 5037 (game `launch-build/launch-main-world.ps1:18-26`). Only the explicit `-InstallApk` switch reaches `adb install -r`; ordinary launch instead checks the installed package/hash and starts its StartupActivity (`launch-main-world.ps1:186-199,211-212`). Installed verification accepts the original installed pin or the published distribution pin (`launch-main-world.ps1:57-63`). **Caveat:** explicit `-InstallApk` validates `$config.apk` against `$config.apk_sha256`, not `distribution_apk_sha256` (`:186-189`); do not assume a freshly staged distribution file is automatically selected for that operation.

## Why two clients/icons are possible

The manifest packager deliberately rewrites the original `com.fl.mhsy.qihoo` identity to `com.fl.mhsy.privateworld` (game `launch-build/multiplayer_manifest.py:91-95`). Different Android package identities can coexist; installing privateworld is not an in-place upgrade of qihoo, and this pipeline's registry/launcher code does not remove qihoo. Game `launch-build/DEV-WORKFLOW.md:19` specifically documents the formerly identical Main icons as retired Opening versus current Main, and reports that retired Opening was disabled while retaining APK/data for rollback. **That is a historical documented state, not a fresh observation that it remains disabled today.** DEV is separately documented as another BlueStacks installation (`DEV-WORKFLOW.md:5-19`).

## Configuration and verification limits

No builds, deploys, tests, emulator/ADB operations, credential access, or existing-file edits were performed. No private/live configuration was inspected. Parent checks actual installed packages and runtime bindings separately. Publication depends on broker `publish_apk`, optional `registry_config`, configured distribution destination, static assets, serving/routing and the installed client's capabilities. The builder uses a configured reviewed `trusted_tooling` snapshot rather than automatically executing game-repository packager changes (runner `scripts/build_client.py:303-304,343`; `docs/client-build.md:1`); game source describes the reviewed design but does not prove the deployed private snapshot/version. An older client without this startup updater cannot be assumed to offer APK upgrades. Do not infer current package enablement, installed version, endpoint reachability, or installed-versus-published hashes from examples or historical notes.
